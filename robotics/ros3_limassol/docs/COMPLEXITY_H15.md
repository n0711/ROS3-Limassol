# H15 — Controlled comparison of synthetic H14 scaling reports

Date: 2026-11-02. Scope: offline comparison of existing H14 JSON reports.
No USB device, radio, robot, ROS process, Raspberry Pi benchmark result or
field deployment is supplied or fabricated by this milestone.

## 1. Question being evaluated

Given two **independent** synthetic benchmark reports using the same declared
workload and environment labels, how do their measured median execution times
compare? H15 provides a descriptive comparison with strict input validation;
it **does not determine** whether asymptotic complexity improved.

For mode `m` and observation count `N`:

```text
r(m,N) = candidate_median_seconds / baseline_median_seconds
relative_change_percent = 100 * (r - 1)
```

A ratio below 1 indicates lower observed median time *in those two samples*.
A ratio above 1 indicates higher observed median time. Neither alone establishes
a reliable speedup or regression without controlled repeated trials.

## 2. Inputs and safety rules

The tool `tools/compare_h15.py` accepts exactly two H14 schema-v1 reports
generated by `tools/benchmark_h14.py`, each no larger than 2,000,000 bytes.
It rejects malformed JSON, duplicate keys, nonfinite times, invalid numeric
types, duplicate/missing mode+size combinations and any report that asserts
physical-link, hard-real-time or Big-O verification.

The reports must agree on all of:

- Observation sizes, order and modes.
- Number of repeats and configured late window.
- Benchmark measurement scope and synthetic source/schema.
- All recorded Python/environment labels.

If any of these differ, H15 emits `status: not_comparable` and an **empty**
`comparison` array. A valid comparison emits `status: descriptive_only`.
No numeric threshold is used to make a performance pass/fail decision.

Matching `platform.platform()` strings are **not sufficient to establish
the same host, CPU frequency, power management settings, background workload,
temperature or scheduler behavior**. H15 explicitly reports
`same_host_verified: false`, even if strings match.

The SHA-256 values in the output identify the exact input JSON bytes; they do
not authenticate the report's origin or establish that its measurements are
independently reproducible.

## 3. Usage: no physical hardware required

Run this in `robotics/ros3_limassol`:

```sh
python3 tools/benchmark_h14.py \
  --sizes 1024 2048 4096 8192 --repeats 3 > ~/h14-baseline.json

# Re-run only after recording environment/commit changes and checking machine load.
python3 tools/benchmark_h14.py \
  --sizes 1024 2048 4096 8192 --repeats 3 > ~/h14-candidate.json

python3 tools/compare_h15.py \
  ~/h14-baseline.json ~/h14-candidate.json > ~/h15-comparison.json
```

Do not use an existing output path if you intend to retain a previous report:
normal shell redirection overwrites files. Keep baseline, candidate and output
under distinct filenames. Never present GitHub Actions timing as a Raspberry
Pi 3B result. The user must execute the benchmark on the Pi to measure that
device.

Inspect:

```sh
python3 -m json.tool ~/h15-comparison.json
python3 -m unittest discover -s tests -p 'test_h15_comparison.py' -v
```

Benchmark numbers are sensitive to the workload and Python version. The H14
workload includes synthetic telemetry construction/JSON serialization,
ingestion and, for replay, lazy synthetic recording generation. H15 never
isolates `LinkMonitor.ingest` latency from those costs and never compares
radio-link or physical sensor performance.

## 4. Asymptotic mathematical boundary

The code-reviewed H13/H14 complexity conclusion remains:

```text
default receive: expected O(N*B)
late-window receive: amortized expected O(N*(B + log(W+1)))
retained state per monitor: O(S + W)
R independent monitors: O(R*(S + W))
```

These bounds use expected hash-table behavior. A single late-window update
may remove O(W) items, making a deterministic O(1) per-update statement
unsupported. A finite-size speed ratio or fitted slope is **not** a proof of
worst-case Big-O complexity.
